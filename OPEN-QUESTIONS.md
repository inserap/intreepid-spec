> Mise à jour pendant les rituels session-end (bins c. additions, d. résolutions).
> Les IDs `Q-NNNN` sont **immuables** : ne jamais réutiliser un Q-NNNN même après résolution.

## Comment utiliser ce fichier

- **Ajouter** un item quand une session fait émerger une vraie ambiguïté non résolvable en séance.
- **Résoudre** un item quand une session livre une réponse (ADR, entrée journal, slice execution).
- **Raffiner** un item quand sa formulation évolue.

| Q-0004 | Schéma du catalogue sémantique et modèle de données de l'arbre/trace (avec attribution et empreintes spatiales) ? | 2026-07-26 | Architecture | Prochaine étape n°3 de l'architecture — conditionne tout le reste. **Raffinements (revue externe 2026-07-26)** : (a) en faire le *premier contrat exécutable* (schéma YAML catalogue + modèle d'événement de trace) avant tout code ; (b) empreinte de reproductibilité d'un insight = hash dataset + version catalogue + SQL + params + versions DuckDB/extensions + modèle + version prompt/charte (le « SQL rejouable » seul ne suffit pas si Parquet/catalogue évoluent) ; (c) invariants géospatiaux du dataset, pas champs descriptifs : SRID (EPSG:2056), reprojection, unités de distance, validité géométrique, version H3 ; (d) contrat MCP read-only à durcir en invariants *testés* : bornes sur sorties + quotas temps/mémoire + whitelist datasets/relations + audit par appel + interdiction écritures indirectes (COPY/INSTALL/extensions). **Raffinement biographie (session 2026-07-26)** : distinguer dans le modèle deux natures de résultat — *fait intrinsèque à la donnée* (vrai quelle que soit la question → promu à la **biographie/fiche**, canal **cross-analyse** partagé) vs *insight sur le monde* (spécifique à une analyse → **graphe de connaissances**, canal par-analyse). La fiche est le confluent où les faits-donnée découverts par **n'importe quelle** analyse s'accumulent (ex. une quirk de la couche routes trouvée via l'analyse accidents sert à l'analyse entretien). Le schéma doit prévoir : (i) un champ de faits-donnée promus avec **provenance** (session + requête, P4), (ii) le critère de promotion « vrai et utile quelle que soit la question », (iii) la promotion **filtrée** curateur→MR humain (garde anti-gonflement de la fiche, cousin de Q-0003 / critique NotebookLM n°3), (iv) rappel : une découverte fortuite reste hypothèse jusqu'à survie au critique/modèle nul (Q-0009) avant promotion. **Raffinement frontière charte↔fiche (brique #1, 2026-07-28)** : à graver — la *posture* (honnêteté fait/hypothèse/refusé, jamais de lignes brutes) reste **générique** dans la charte des agents ; la *connaissance per-dataset* (pièges, sens des colonnes, codes sentinelles) vit dans la **fiche**, lue via `describe` au runtime. C'est ce partage qui permet « traiter n'importe quelles données » sans gonfler le prompt. La charte de la brique #1 porte du **surajustement de scénario** (exemple `999`, instruction « concentration → hypothèse » tunée pour l'oracle) → à extraire vers la fiche / des exemples neutres lors de la généralisation **sur un 2ᵉ dataset réel** (ne se fera pas tout seul — dette à solder délibérément). |
